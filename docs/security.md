# Security model

Every application table has RLS and explicit SELECT, INSERT, UPDATE and DELETE policies restricted to the `authenticated` role and scoped to `(select auth.uid())`. Composite foreign keys prevent cross-user references even when identifiers are guessed. Google is the only UI authentication method and requests identity-only scopes. Sessions use Supabase SSR cookies; server layouts verify users. Redirects accept only same-origin relative paths. Text length and structural constraints exist in both Zod and PostgreSQL. User HTML is never rendered. Account deletion requires an authenticated session, a same-origin request, an explicit confirmation header and a per-user rate limit.

Authenticated pages are marked `private, no-store`. The service worker caches only the public shell and immutable static assets, never private workspace navigations. Cached workspace snapshots remain local to the browser for offline use and are removed together with pending operations when the user signs out or deletes the account. The account-deletion response also requests browser storage and cache removal through `Clear-Site-Data`.

Internal telemetry accepts only small same-origin JSON requests, records sanitized technical metadata and never records user content. Rate-limit storage is bounded to prevent unbounded process memory growth. Browser defenses include CSP, frame denial, MIME sniffing protection, cross-origin resource policies and a restrictive permissions policy.

The publishable key is intentionally browser-safe; the service-role key must exist only in server environment variables and is reserved for verified account deletion. Operators must disable unused Supabase providers, keep dependencies patched, configure exact OAuth redirects, review CSP changes and rotate credentials if exposed. RLS must never be disabled in production. In-memory rate limits are defense in depth for a single runtime instance; infrastructure-level rate limiting should be used if abuse volume requires a global limit.
