# Security model

User-data tables have authenticated, owner-scoped RLS policies using `(select auth.uid())`, with explicit grants for allowed operations; immutable completion history intentionally has no UPDATE policy. Composite foreign keys prevent cross-user references even when identifiers are guessed. Google is the only UI authentication method and requests identity-only scopes. Sessions use Supabase SSR cookies; server layouts verify users. Redirects accept only same-origin relative paths. Text length and structural constraints exist in both Zod and PostgreSQL. User HTML is never rendered. Account deletion requires an authenticated session, a same-origin request, an explicit confirmation header and a per-user rate limit. Backup restoration authenticates, consumes a fail-closed per-user distributed rate limit, and replaces the workspace through `restore_planora_backup`. That wrapper is `SECURITY DEFINER` with an empty `search_path` so it can call `restore_planora_backup_core` without exposing `_core` to PostgREST; every delete and insert is still bound to `auth.uid()`. Direct execute on `_core`, `assert_restore_rate_limit` and `restore_category_scope` is revoked from `anon` and `authenticated`.

Authenticated workspace pages — including Today, Week, Month, Search, Summary, Tasks, Focus and the remaining app routes — are marked `private, no-store`. The service worker caches only the public shell and immutable static assets, never private workspace navigations. Cached workspace snapshots remain local to the browser, are size-bounded and structurally validated before use, and are removed together with pending operations when the user signs out or deletes the account. The account-deletion response also requests browser storage and cache removal through `Clear-Site-Data`.

Internal telemetry reads at most 4 KiB before parsing, including chunked requests, and retains only allowlisted technical metadata and canonical route names. Raw messages, URL parameters and arbitrary context are omitted. Account deletion denies the request if the distributed limiter is unavailable; limiter requests have a timeout. Telemetry may fall back to a bounded per-instance memory bucket. Browser defenses include CSP, frame denial, MIME sniffing protection, cross-origin resource policies and a restrictive permissions policy. Login and private pages use a fresh cryptographic script nonce forwarded to Next.js rendering; their policy does not allow inline scripts without a nonce. Public static pages retain the compatible inline-script policy needed by their cached shell. Public-to-login links perform document navigation so the private policy takes effect.

The publishable key is intentionally browser-safe; the service-role key must exist only in server environment variables and is used for verified account deletion and the distributed rate-limit RPC. Operators must disable unused Supabase providers, keep dependencies patched, configure exact OAuth redirects, review CSP changes and rotate credentials if exposed. RLS must never be disabled in production.

Build-time checks reject non-HTTPS deployment origins (except loopback development), credentials embedded in origins, and privileged keys assigned to the public publishable-key variable. Session cookies are host-only, SameSite=Lax and Secure over HTTPS. They remain JavaScript-readable because the current Supabase browser client owns token refresh and direct REST access; this is not an HttpOnly/BFF architecture.

Account deletion additionally requires verified JWT authentication-method proof from the last ten minutes, bound to the verified user. Refreshing a token does not reset that age. An older session must sign in with Google again and repeat the confirmed deletion. Success clears cookies, cache and storage. A central session guard removes private UI and polling on sign-out or account changes across tabs; session generations prevent old asynchronous completion/Focus work from recreating cleared local data.

Failed restore payloads and constraint failures return sanitized JSON failure results while preserving an outer SQL attempt counter. Workspace changes alone roll back in a nested savepoint; deferred constraints are checked inside it. Successful results include `ok:true` beside existing counts. The Server Action and direct RPC have separate five-per-hour admission namespaces. Transaction cancellation, connection abort and server timeout still require gateway controls because they abort outer accounting as well.

Database CHECKs bound JSON bytes, Focus segments and distractions independently of application validation. Per-owner INSERT quotas use a shared transaction lock and one count per statement, including bulk restore. New CHECKs are `NOT VALID` to preserve existing rows; new inserts and updated rows are checked. Review pre-existing oversized data and quota usage before rollout. See [the October hardening record](security-hardening-2026-10-30.md) for limits, verification and deployment obligations.

Completing or undoing a task records the last action in `task_occurrence_state`. Offline replay consults that row so a newer uncomplete on another device is not overwritten by an older queued complete. System notifications while a fully suspended PWA is in the background remain an OS/browser limit.

Focus tables (`focus_presets`, `focus_sessions`, `focus_intervals`, `focus_goals`) follow the same RLS and ownership-FK model. A partial unique index enforces one active session per user. Session notes and parked distractions are private account data: they appear in full JSON backups, are omitted from analysis CSV by default, and must never be sent to product analytics or system notification bodies. Live sessions are terminalized on restore so timers and notification schedules are not resurrected without user action.
